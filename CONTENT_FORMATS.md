# RC Car King scheduled article formats

Authorized cadence from 14 October 2026, Europe/Skopje: three vehicle reviews each weekday at 09:00, one listicle each Monday at 10:00, and one guide each day at 11:00, including weekends. All schedules continue in the existing RC Car King chat and publish to AlekSpasSEO/rc-car-king and https://rccarking.com. The times start the work; publication follows completed research and validation.

Read CONTENT_GUIDE.md, EDITORIAL_VOICE.md and CLOUDFLARE.md on each run. Preserve the original Garage Editor voice, current design, author identity, disclosure policies, production domain and separate GitHub preview. Do not invent physical testing, personal ownership, measurements, quotes, endorsements, review stars or reliability statistics. Practical guidance about operation and maintenance may discuss equipment, but the current product-review and buying-list scope remains complete vehicles and body-inclusive kits; no standalone spare-part, shell or bare-chassis reviews or buying roundups.

## Weekly listicle

Publish one original article in the current Monday–Sunday week. Count only newly published listicles, not edited older pages, and skip when that week's article already exists. Use `/listicles/topic-slug/`. Pick a useful, specific buying question and vary use, budget, terrain and experience level across weeks. Begin with the existing researched review archive and verify current manufacturer evidence and exact variants again where needed.

Aim for roughly 1,800–2,800 useful words. For a vehicle buying list, normally select five to eight complete cars, using fewer when the evidence supports a tighter list. Give a quick recommendation table, clear inclusion/selection criteria, the intended buyer and course, each exact model/SKU, strengths, reservations, included versus required equipment, a realistic startup-cost basis, and links to its full review. Explain why each pick belongs and who should skip it. Close with how to choose, useful FAQs and dated sources. Do not claim an objective best, a physical comparison test or a sales ranking without evidence. Non-buying numbered articles must be equally practical and sourced; do not force product recommendations into them.

Any Amazon purchase link must be verified through scripts/amazon.mjs against exact ASIN, manufacturer SKU, brand and package, use coffeedant03-20, and carry sponsored/nofollow attributes with visible disclosure. Reuse verified archive identities when applicable. Do not substitute approximate keyword matches. Manufacturer reference prices must have currency, check date and a labeled basis; Amazon offers belong only in the existing expiring API display. If live offer retrieval fails, keep a previously verified link and omit the price.

## Daily guide

Publish one original how-to, informational explanation or practical guide per calendar day, including weekends. Count newly published guides by their Europe/Skopje publication date, not modification date, and skip when today's guide already exists. Use `/guides/topic-slug/`. Rotate beginner setup, vehicle categories, terrain choice, driving controls, troubleshooting and ownership topics. Check the archive for overlapping intent before selecting a topic.

Aim for roughly 1,200–2,200 useful words, letting topic complexity determine the length. Answer the reader's question near the top. Include scope and assumptions, the necessary equipment or model-specific prerequisites, ordered steps when the topic is procedural, explanations of why those steps matter, common mistakes and troubleshooting, a concise completion checklist, relevant full-review links, useful FAQs and dated primary sources. Clarify model and electronics differences rather than present one manual's procedure as universal. For charging, electrical setup or other safety-sensitive operations, use current manufacturer instructions and verified compatibility limits; do not improvise bypasses or unsupported settings.

Product links should help complete the task and need not appear in every guide. Apply the same exact-product affiliate checks and disclosure rules when buying links are useful. Use attributed official photographs or clear original diagrams when they explain the topic. No unlicensed community images or fabricated demonstration photos.

## Implementation and publication

Store durable article content and evidence in tracked source files, separate from `content/reviews`. If the current generator does not yet support these article types, the first scheduled run should add minimal reusable article rendering and validation before publishing its first article. Do not force an informational article into a vehicle review record, make up a product box/rating, leave an unrendered Markdown draft as the publication, or hand-edit generated HTML that the next build will remove.

Give articles distinct SEO titles/descriptions, HTTPS production canonicals, matching Open Graph/Twitter values, real publication/modification timestamps, visible author/date/source details, and Article/WebPage/BreadcrumbList schema. Use ItemList for a real list of picks and FAQPage only for matching visible questions. Do not add Product/Review or customer ratings to a guide merely to chase search features. Keep schema values aligned with visible content and existing linked publisher identities.

Make published articles discoverable through appropriate listicle/guide index pages, navigation or a small secondary homepage section while preserving the vehicle-review filter. Include them in the HTML site map, XML sitemap index/child pages sitemap, RSS and llms.txt. Preserve the current preview noindex setting and production indexing. Update checker coverage for new routes, internal links, unique metadata, actual structured-data facts, affiliate attributes and draft/future exclusions. Blank formats should not create public placeholder pages.

Before editing, safely sync main and inspect local changes; do not overwrite another publishing run or owner work. Commit only complete validated work. Use the existing in-chat scheduling context to avoid concurrent writes; if a previous publication is still active, let it finish before syncing and publishing the next format. Never reset or force-push to resolve a race.

Run `npm run build` and `npm run check` for the production and preview profiles, inspect desktop/mobile output, and commit source/content plus generated docs together. Refresh Amazon offers independently with the existing scripts and authorized local CSV or environment credentials, including on guide days so weekend offers can remain fresh. Keep credentials in memory and out of Git, logs and browser code. Push main and verify the matching successful Cloudflare deployment, using the existing Git-branch API fallback when necessary. Verify the production article URL and archive links before reporting publication. Report meaningful failures without pretending a draft or failed deployment is live; stay quiet when there is no new publication or actionable change.
